Vector store operations notes

These notes collect practical lessons from running a small retrieval-augmented generation service on a single container with about 1 GB of memory. They cover index parameters, distance metrics, re-embedding and day-to-day maintenance.

HNSW parameters

Most embedded vector stores, including ChromaDB, build an HNSW (Hierarchical Navigable Small World) graph. Three parameters matter. M is the number of links each node keeps; higher values improve recall but cost memory, roughly M x 2 x 4 bytes per vector for the graph alone. ef_construction controls how many candidates are explored while building the graph; raising it from 100 to 200 makes indexing slower but gives a better graph. ef (also called ef_search) controls how many candidates are explored at query time; it should always be at least the number of results requested. For a few thousand chunks the defaults (M = 16, ef_construction = 100) are fine, and tuning ef is usually the only change worth making.

Cosine distance versus L2

Embedding models such as bge-small produce normalized vectors, so cosine distance and L2 distance give the same ranking. Cosine is still the safer default: it keeps working if a future model returns vectors that are not normalized. Store the metric in the collection metadata (for ChromaDB, hnsw:space = cosine), because it cannot be changed after the collection is created. Cosine distance in ChromaDB is 1 minus the cosine similarity, so 0 means identical and values near 1 mean unrelated.

Re-embedding after a model change

Vectors from different embedding models are not comparable, not even when they have the same number of dimensions. When the model changes, create a new collection named after the model and re-embed everything into it; never mix two models in one collection. Keep an embedding cache keyed by the model name and a hash of the exact text, so unchanged text is never embedded twice, and so switching back to an earlier model costs nothing.

Memory on small containers

ONNX Runtime grows its memory arena to fit the largest batch it has processed and rarely returns it. On a 1 GB container, embed in batches of one to four texts, use one or two threads, and set MALLOC_ARENA_MAX=2. A cross-encoder reranker can add more than 200 MB per request; turn it off in production and keep it for offline evaluation.

Hybrid search

Dense vectors miss exact identifiers such as header names, error codes and acronyms, while BM25 misses paraphrases. Run both and merge the ranked lists with Reciprocal Rank Fusion, which needs no score normalization. Keep keyword statistics per collection or per tenant: if term frequencies are shared, one tenant's uploads change another tenant's scores.

Maintenance checklist

1. Back up the persistent directory together with the metadata database, never one without the other.
2. After a crash, rebuild in-memory keyword indexes from the vector store, which is the source of truth.
3. Delete per-session collections on a timer, and measure memory after each change with the platform's metrics.
4. Log ids, sizes and timings only; never log document text.
